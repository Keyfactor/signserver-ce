Secure Audit Log

The CESeCore secure audit log is the default log for SignServer, used for system and audit logging. The secure audit log provides options for signed logs, an Audit Record Data table, and an alternative integrity-protected log device.

Signed Log

enterprise

An example configuration for CESeCore is provided in conf/cesecore.properties.sample.

To enable signed audit logs, configure conf/databaseprotection.properties (see conf/databaseprotection.properties.sample).

Also, set the following to enable signing of the Audit Record Data table as well as verification of the log entries queried using, for instance, the CLI:

databaseprotection.enablesign.AuditRecordData = true
databaseprotection.enableverify.AuditRecordData = true

If enableverify is set to true, all individual log entries that are displayed using CLI, Admin Web, or over web services are verified on the server side. In case of inconsistent signatures, an error message is displayed. This verification will not discover missing log entries. To verify the complete log for all nodes as well as detect gaps in the sequence numbering, run the Database CLI.

Each SignServer node writing to the audit log needs to use different node IDs. By default, the hostname is used. If multiple instances are running from the same host, set the node ID manually in conf/cesecore.properties as cluster.nodeid.

If signing or verification is enabled, one or more Crypto Tokens needs to be configured.

Example: PKCS#11 using Default Provider

It is recommended to use the same type of PKCS#11 provider for database protection as the other Signers are also using. If the Signers are using the PKCS#11 Crypto Token, the following Crypto Token called org.cesecore.keys.token.PKCS11CryptoToken should be used:

databaseprotection.keyid = 400
databaseprotection.keyid.0 = 400
databaseprotection.keylabel.0 = dbProtKey
databaseprotection.classname.0 = org.cesecore.keys.token.PKCS11CryptoToken
databaseprotection.properties.0 = sharedLibrary=/opt/utimaco/Software/PKCS11/lib/Linux-x86-64/libcs2_pkcs11.so, slotLabelType=SLOT_NUMBER, slotLabelValue=1
databaseprotection.data.0 =
databaseprotection.tokenpin.0 = userpin1
databaseprotection.version.0 = 2

Example: PKCS#11 using P11NG Provider

It is recommended to use the same type of PKCS#11 provider for database protection as the other Signers are also using. If the Signers are using the P11NG Crypto Token, the following Crypto Token called org.signserver.p11ng.common.cryptotoken.P11NGDatabaseProtectionCryptoToken should be used:

databaseprotection.keyid = 400
databaseprotection.keyid.0 = 400
databaseprotection.keylabel.0 = dbProtKey
databaseprotection.classname.0 = org.signserver.p11ng.common.cryptotoken.P11NGDatabaseProtectionCryptoToken
databaseprotection.properties.0 = SHAREDLIBRARYNAME=Utimaco, SLOTLABELTYPE=SLOT_NUMBER, SLOTLABELVALUE=1, pin=userpin1
databaseprotection.data.0 =
databaseprotection.tokenpin.0 = userpin1
databaseprotection.version.0 = 2
databaseprotection.sigalg.2 = SHA256WithRSA

Example: REST DSM using EJBCA Fortanix Crypto Token

To enable database protection using Fortanix REST API, the API token must be provided in the databaseprotection.properties file.

databaseprotection.keyid = 400
databaseprotection.keyid.0 = 400
databaseprotection.keylabel.0 = dbProtKey
databaseprotection.classname.0 = org.signserver.server.enterprise.cryptotokens.CryptoTokenAdapter
databaseprotection.properties.0 = implementationClass=org.ejbca.keys.token.FortanixCryptoToken, fortanixBaseAddress=https://apps.smartkey.io
databaseprotection.tokenpin.0 = api-token
databaseprotection.data.0 =
databaseprotection.version.0 = 2
databaseprotection.sigalg.0 = SHA256WithRSA

Example: REST HSM using Azure Key Vault

To enable database protection using Azure Key Vault REST API, the name of the key vault, a client ID, vault type (standard or premium), and secret must be provided in the databaseprotection.properties file.

databaseprotection.keyid = 400
databaseprotection.keyid.0 = 400
databaseprotection.keylabel.0 = dbProtKey
databaseprotection.classname.0 = org.signserver.server.enterprise.cryptotokens.CryptoTokenAdapter
databaseprotection.properties.0 = implementationClass=org.cesecore.keys.token.AzureCryptoToken, keyVaultName=vault-name, keyVaultClientID=client-id, keyVaultType=standard/premium
databaseprotection.tokenpin.0 = secret
databaseprotection.data.0 =
databaseprotection.version.0 = 2
databaseprotection.sigalg.0 = SHA256WithRSA

Alternative Integrity Protected Log Device

By default, the IntegrityProtectedLogDevice logs audit data to the database. If the database or HSM is unavailable during logging, gaps in sequence numbers may appear. These gaps correspond to failed logging attempts, not missing operations, since logging occurs before execution. The counter values are incorrect, but no log entries are lost. Correlate these gaps with error messages in other logs for database or HSM failures.

Alternative Device

To avoid sequence gaps, use SequentialIntegrityProtectedLogDevice. The device logs entries one at a time, ensuring each succeeds before proceeding.

The disadvantage of this alternative option is significantly reduced performance.

Configuration

To configure the alternative device:

  1. Edit conf/cesecore.properties.

  2. Comment out the default IntegrityProtectedLogDevice.

  3. Enable SequentialIntegrityProtectedLogDevice as shown in the example:

#securityeventsaudit.implementation.1=org.cesecore.audit.impl.integrityprotected.IntegrityProtectedDevice
securityeventsaudit.implementation.1=org.signserver.server.integrityprotected.SequencialIntegrityProtectedDevice

SignServer must be redeployed for the changes in conf/cesecore.properties to take effect.
